# Qwen CPU Decode Stage Comparison - 2026-08-09

## Scope

This report consolidates the accepted Qwen CPU decode measurements into one implementation decision record. It
compares LiteNN CPU AOT with the strongest locally reproduced CPU-only llama.cpp control, separates the reference FFN
activation from its Down projection, and identifies which differences are strong enough to schedule work.

The detailed experiment records remain authoritative for their individual campaigns:

- full-token build/runtime control: `docs/QwenCPUDecodeBuildControl_2026-08-04.md`;
- accepted low-overhead stage method: `docs/QwenCPUDecodeStageControl_2026-08-04.md`;
- LiteNN activation and artifact evidence: `docs/QwenCPUDecodeSwiGLUEvidence_2026-08-09.md`;
- Clang activation/Down split: `docs/QwenCPUDecodeActivationDownSplit_2026-08-09.md`;
- GNU compiler cross-check: `docs/QwenCPUDecodeGNUStageControl_2026-08-09.md`.

This report does not combine non-adjacent runs into a synthetic end-to-end benchmark. It uses adjacent paired runs for
the whole-token claim and uses stage/helper measurements only to rank implementation ownership.

## Measurement Boundary

- Workload: Qwen2.5-Coder-14B-Instruct Q4_K_M, `8,988,110,272`-byte GGUF.
- Host: AMD Ryzen 9 9950X on Windows under the balanced power policy.
- Reference revision: llama.cpp `b81c2cdd748dc2704d5989cf03936325554c12d3`.
- Reference build selected for the primary control: Clang `22.1.8`, Release `-O3`, native ISA, OpenMP disabled.
- Compiler cross-check: GCC `16.1.0`, Release `-O3`, native ISA, OpenMP disabled.
- Decode policy: 8 threads, 9 fixed prompt tokens, 15 fixed generated-token evaluations, alternating run order.
- Correctness gates: identical generated bytes/token ids where applicable, required LiteNN AOT cache hit, and no
  fallback.

Private model and executable paths are omitted. Raw process artifacts remain under ignored `build` directories.

## Whole-Token Control

The strongest adjacent three-pair actual-completion control produced:

| Runtime | Median throughput | Independent-median latency | CV |
| --- | ---: | ---: | ---: |
| llama.cpp Clang/no-OpenMP | `5.970 token/s` | about `167.5 ms/token` | `1.82%` |
| LiteNN CPU AOT | `5.518 token/s` | about `181.2 ms/token` | `1.92%` |

The preferred median of adjacent per-pair differences places LiteNN `5.49%` behind. The ratio of independent medians
would place it `7.57%` behind, but that statistic is more exposed to host-state drift between non-adjacent runs. Both
runtimes passed output, fallback, variance, and sampled-frequency gates.

The separately observed external `6.85 token/s` result is not an accepted baseline. Its binary and complete
build/runtime provenance have not been reproduced, so it cannot select a LiteNN kernel. It remains a parallel evidence
task.

## Stage Comparison

The two reference compilers agree on the stage composition:

| Normalized reference stage | Clang ms/token | GNU ms/token | GNU minus Clang |
| --- | ---: | ---: | ---: |
| Attention | `36.846` | `36.338` | `-0.508` |
| FFN Gate/Up | `70.916` | `70.564` | `-0.352` |
| FFN activation | `0.210` | `0.196` | `-0.014` |
| FFN Down | `43.045` | `43.128` | `+0.083` |
| Final logits | `11.920` | `11.739` | `-0.181` |

Compiler choice does not materially reorder the stages. In particular, both builds place SwiGLU activation near
`0.2 ms/token` and Down near `43 ms/token`.

LiteNN's stable helper accounting is compared with the Clang full-stage result below. The LiteNN rows are helper lower
bounds from a separate cache-hit campaign; a lower LiteNN number does not prove that the containing full stage is
faster. A LiteNN helper lower bound that already exceeds the complete reference stage, however, is sufficient to
identify a deficit.

| Component | LiteNN helper lower bound | Clang reference stage | LiteNN minus reference | Decision |
| --- | ---: | ---: | ---: | --- |
| Attention | `36.226 ms` | `36.846 ms` | `-0.620 ms` | no deficit established |
| FFN Gate/Up | `65.048 ms` | `70.916 ms` | `-5.868 ms` | no deficit established |
| FFN activation | `11.043 ms` | `0.210 ms` | `+10.833 ms` (`52.5x`) | confirmed P0 owner |
| FFN Down | `42.723 ms` | `43.045 ms` | `-0.322 ms` | no deficit established |
| Final logits | `10.995 ms` | `11.920 ms` | `-0.925 ms` | no deficit established |

Activation accounts for about `84%` of the previously accepted `12.892 ms` composite activation-plus-Down gap. Its
`10.833 ms` deficit is also the same order as the complete local paired gap, but these campaigns are not adjacent and
the value is an optimization ceiling rather than a promised whole-token saving.

## Instruction and Microbenchmark Evidence

Release disassembly of `litenn_cpu_swiglu_f32` shows one scalar `expf` call per lane and no YMM/ZMM vector body. Moving
the production-shape 48-call benchmark from contiguous to stride-2 inputs changes mean time by only about `1.5%`, so
layout and call dispatch are not the primary owner.

The same benchmark executable compared LiteNN's strict scalar path with the bounded implementation already present in
the pinned GGML benchmark dependency:

| Math policy | 48-call mean | Median | CV | Maximum absolute/relative error |
| --- | ---: | ---: | ---: | ---: |
| LiteNN strict scalar `std::exp` | `15.8 ms` | `15.9 ms` | `7.94%` | `0 / 0` |
| Bounded GGML control | `0.526 ms` | `0.529 ms` | `1.04%` | `9.54e-7 / 3.47e-7` |

The bounded control is about `30x` faster and saves about `15.3 ms` in this isolated 48-layer sequence, with no
observed signed-zero, infinity, or NaN mismatch. This clears the standalone promotion threshold, but it does not
authorize a silent numerical-policy change or linking the full GGML runtime into LiteNN.

## Conclusions

1. Bounded vector SwiGLU is the only current CPU implementation P0 selected by accepted cross-runtime evidence.
   LiteNN's strict scalar exponential loop owns a confirmed `10.833 ms/token` stage deficit.
2. Q4_K/Q6_K Down, Gate/Up, logits, compiler switching, and another worker wake-policy change are closed until a new
   accepted profile identifies a concrete deficit. Their current measurements do not justify implementation work.
3. The existing standalone/fused strict-versus-bounded compiler and artifact contract is necessary but not yet an
   optimization: bounded artifacts remain unsupported until LiteNN owns a real vector-math provider and executable
   helpers.
4. The provider decision is the immediate dependency. The preferred path is a maintained cross-platform provider such
   as SLEEF; the smaller alternative is an attributed compact kernel derived from the pinned GGML implementation.
5. The bounded helper must first preserve the declared error, saturation, special-value, ISA-fallback, and
   cross-platform contracts. It then needs the 48-call benchmark gate and three alternating exact-token full-model
   pairs before it can become a retained production option.
6. The current 15-token window is sufficient for hotspot selection but not for a sustained-throughput claim. A
   128-token control is the next validation tier, followed by 512 tokens and capacity-aware 2K/32K/128K/1M context
   tiers.
7. Reproducing `6.85 token/s` is independent of the activation implementation. Even a successful activation fix cannot
   explain an unverified binary/configuration difference, so no second kernel P0 should be inferred from that number.

## Ordered Acceptance Plan

- [ ] Select the vector-math ownership boundary and record dependency/license/platform implications.
- [ ] Implement bounded standalone and fused SwiGLU helpers behind the existing explicit policy and capability ABI.
- [ ] Pass special-value, maximum-error, saturation, ISA-dispatch, object import/load, and cross-platform execution
  tests while keeping `Strict` the default.
- [ ] Require at least `2x` or `5 ms/token` improvement in the 48-call production-shape benchmark.
- [ ] Run three alternating exact-token, AOT-cache-hit LiteNN/reference pairs; require unchanged output, no fallback,
  at least `3%` median token-latency gain, activation-plus-Down within `10%`, and total latency within `5%` of the
  adjacent reference.
- [ ] Repeat the accepted five-stage profile to verify that the activation deficit, rather than an unrelated stage,
  actually moved.
- [ ] Extend the paired window to 128 and 512 generated tokens, recording sustained throughput, variance, memory
  residency, and cache growth.
- [ ] In parallel, obtain the external `6.85 token/s` binary or exact provenance and require two accepted paired
  batches before using it as a target.
